Run AI on your own hardware

Chapter 01

Running a model locally

Three parts work together on a computer you control: the model file, the engine that runs it and the interface you type into.

Running a model locally means the AI works on hardware you control, such as your own laptop or a server in your office. Your questions and documents are processed on that machine and are not sent to an online service.

1. You type a question

The interface is where you type and read. It can be the chat window of a desktop app, a chat page in your browser, or a program of your own.

2. The question goes to the engine

The interface passes your text to the engine, the program that does the actual work. Running a model like this is called inference. The engine first splits the text into tokens, which are pieces of words.

3. The engine works through the model file

The model file holds billions of numbers learned during training, called weights or parameters. The engine loads the file into memory once. For every token it writes, it runs a calculation through those weights.

4. The answer arrives token by token

Each new token goes back to the interface as soon as it is ready, which is why answers appear word by word. The engine adds the token to the text and repeats until the answer is complete.

Model file

A file of a few gigabytes up to several hundred, downloaded once, usually from Hugging Face. Qwen3.5 9B, for example, is about 6 GB in its common 4-bit version.

Engine

The program that loads the model and calculates the answer. llama.cpp, MLX and vLLM are engines.

Interface

Where you type and read: a desktop app, a web page such as Open WebUI, or your own program connected through an API (an agreed way for programs to send each other requests).

Desktop apps such as Ollama, LM Studio and Jan bundle all three. They download model files, include an engine and give you a chat window.

Why people run models locally

Privacy
Prompts and files stay on hardware you control. That matters for personal data, client files and unpublished work.
Cost at high volume
Once you own the hardware, each extra answer costs only electricity. With heavy, steady use this can be cheaper than paying an online service per token. With light use it is usually more expensive. Chapter 11 compares the options.
Works offline
It runs without an internet connection, for example on a train or in a network cut off from the outside.
Control
The model only changes when you change it. Online services update and retire their models on their own schedule.
Customisation
You can choose a model for your language or field, change its settings, or train it further on your own examples (fine-tuning).

The downsides

Smaller models
Models that fit on ordinary hardware are smaller than the largest online services and make more mistakes on hard tasks. The biggest open models need servers with several large graphics cards.
You maintain it
Installing, updating, securing and backing up the system is your job.
Speed depends on hardware
A laptop without a graphics card works, but slowly.
Up-front cost
Hardware is paid for in advance, whether it is busy or idle.
When a local set-up can still send data out

The model file itself cannot send anything. The program around it can: some apps check for updates, collect usage statistics or offer optional online models next to the local ones. Read the privacy settings, switch off what you do not need, and block the program's network access if you must be certain.

Chapter 02

Memory decides what fits

The whole model file has to fit into memory, and its size is roughly the number of parameters times the bytes stored for each one.

When the engine starts, it loads the entire model file into memory. If the file is larger than the memory available, the model either does not start or runs very slowly, because parts of it must be fetched from slower memory for every token.

Parameters and bytes

A model consists of billions of numbers called parameters. The name usually says how many: “9B” means 9 billion. At full 16-bit precision each parameter takes 2 bytes, so a 9B model is about 18 GB. That is too big for a laptop with 8 or 16 GB of memory.

The same model at 4-bit

Stored at 4-bit, each parameter takes a little over half a byte and the file shrinks to about 5.5 GB. Now it fits on a laptop with 16 GB, with room left for the conversation. Chapter 3 explains how this works.

A mid-sized model

A 30B model at 4-bit is about 18 GB. It needs a graphics card with 24 GB of memory or a computer with plenty of shared memory.

The largest open models

The biggest open models have several hundred billion to more than a trillion parameters. Even at 4-bit, a model with a trillion parameters is about 600 GB and needs a server with eight large graphics cards.

Move the slider to try other sizes.

Three kinds of memory

Graphics memory (VRAM)
Sits on the graphics card (GPU). It is very fast and limited in size: usually 8 to 32 GB on gaming cards and 80 GB or more on server cards.
System memory (RAM)
The computer's main memory. It is larger and cheaper but several times slower to read, so a model running from RAM writes slowly.
Unified memory
One pool shared by the processor and the graphics part, as in Apple silicon Macs and mini PCs with AMD Ryzen AI Max chips. It is slower than graphics memory but can be much larger, so these machines can hold big models. The system keeps part of it for itself; on a Mac with plenty of memory, roughly a quarter by default.

If a model is a little too large for the graphics card, engines such as llama.cpp can keep part of it in system RAM. This is called offloading. The model runs, but every token waits for the slower memory. The Models page tells you when a model would rely on system RAM.

Why files are a little bigger than parameters × bytes

Quantised files store a small scale value for every group of weights, so a “4-bit” file averages about 4.8 to 4.9 bits per weight. On top of the file, the engine needs room for the conversation memory (chapter 5) and its own working space, usually one to a few gigabytes.

Chapter 03

Quantisation: smaller files

Quantisation stores each of the model's numbers with fewer bits, which makes the file several times smaller at a small cost in quality.

A model's weights are usually published as 16-bit numbers. Quantisation stores them with fewer bits, much like rounding 0.0183472 to 0.018: each number takes less space and becomes slightly less exact. A model with billions of weights tolerates small rounding errors well, up to a point.

In practice the weights are rounded in small groups of 16 to 32. Each group keeps its own scale at higher precision, and every weight in the group is stored as one of a fixed number of steps on that scale. With 4 bits there are 16 steps; with 2 bits only 4. The effect on quality is comparable to saving a photo at a lower JPEG setting: hard to notice at moderate settings, obvious at the extreme.

The quality notes in the demo are typical results for chat use. The loss is usually smaller for large models than for small ones, and it shows first in exact tasks such as maths, code and less common languages.

Models released already compressed

Some labs publish their models at 8-bit or 4-bit from the start, or train them knowing they will be rounded. The second method is called quantisation-aware training (QAT), and it makes the 4-bit version lose less. For such models the original file is already small, and a higher setting adds size without adding quality. Google, for example, publishes official QAT 4-bit files for Gemma 4.

Conversation memory can be quantised too

Engines can also store the conversation memory (chapter 5) at 8-bit or 4-bit. 8-bit halves its size with almost no visible effect. 4-bit saves more but can hurt quality on long documents.

Chapter 04

Memory speed sets writing speed

For each token it writes, the engine reads the model's active weights from memory, so the speed of the memory decides how fast text appears.

A language model writes one token at a time. For each token, the engine reads every active weight from memory once and calculates with it. Reading billions of numbers takes longer than the arithmetic, so on most hardware the speed of the memory sets the writing speed. That speed is called bandwidth and is measured in gigabytes per second (GB/s).

Upper limit: tokens per second ≈ memory bandwidth ÷ gigabytes read per token. A graphics card that reads 1,000 GB/s can read a 17 GB model about 60 times per second, so it writes at most about 60 tokens per second. Real engines reach part of that limit.

Tokens and words

A token is a piece of text: a short word, part of a longer word, or a punctuation mark. In English, 100 tokens are roughly 75 words. German, Swedish and most other languages need more tokens for the same text, so they appear a little more slowly.

Most adults read about 4 words per second. The Models page calls 6 tokens per second “usable” and 15 or more “runs well”.

Reading the prompt comes first

Before the first word appears, the engine reads your whole prompt, including any pasted documents. This step, called prompt processing, handles many tokens at once and is limited by calculating power more than by memory speed. Graphics cards are very good at it; processors without one are slow.

Thinking models take longer to start

Some models first write out their reasoning, which most apps fold away, and only then the answer. These thinking tokens are produced at the same speed as the answer. gpt-oss and GLM-5.3, for example, always think; other models let you switch it off or choose a lower effort.

Several users at once

When several people use a server at the same time, the engine reads the weights once per step and calculates the next token for all of their conversations together. This is called batching. Each person gets nearly the speed of a single user while the machine's total output grows several times. llama.cpp and Ollama can serve a few requests at once; vLLM and SGLang are built to do it at large scale.

Chapter 05

Context and conversation memory

The text a model keeps in view needs memory of its own, and every person using the model at the same time needs a separate share.

The context is all the text the model can see at once: its instructions, the conversation so far, any documents you added and the answer it is writing. It is measured in tokens. 8,000 tokens are about 12 pages of text; 128,000 tokens are about 200 pages.

So that it does not have to re-read the whole context for every new token, the engine keeps intermediate results for each token it has seen. This store is called the KV cache (key-value cache); this guide calls it conversation memory. It grows with every token and sits in memory next to the model.

How fast it grows depends on how the model is built. Older designs store a full entry for every token in every layer. Most models released in 2026 store it in only some of their layers or in compressed form, and need far less.

Every conversation has its own cache. Ten people working with long documents at the same time need ten caches, so on a shared server the conversation memory can be larger than the model itself.

Ways to save conversation memory

Set a shorter context in the engine if you do not need the maximum. A model's maximum context is a limit, and you can use less. Store the cache at 8-bit, which halves it. For a shared server, choose a model with a small cache. The Sizes page and the Calculator let you set the context length and the number of users.

Chapter 06

Mixture of experts

Some large models use only a small part of their weights for each token, so they need a lot of memory but write quickly.

In a dense model, every weight takes part in every token. A mixture-of-experts (MoE) model splits part of each layer into many smaller blocks called experts. A small routing step picks a few experts for each token, and the others are not used for that token.

All experts have to be in memory, because the next token may need different ones. Only the chosen experts are read, so the model writes about as fast as a much smaller dense model. MoE models are often named with two numbers: 35B-A3B means 35 billion parameters in total and about 3 billion active per token.

Despite the name, experts do not divide the work by subject such as law or cooking. The split is learned during training and is hard for people to interpret.

Because only a few experts are read per token, MoE models stay usable when part of them sits in slower system RAM. llama.cpp can keep the experts in RAM and the rest of the model on the graphics card, so a gaming PC can run MoE models larger than its graphics memory.

MoE with many users at once

On a shared server, different users' tokens choose different experts, so each step reads a larger part of the model. The speed advantage over a dense model of the same total size therefore shrinks as the number of users grows. The memory needed stays the same: all experts are always loaded.

Chapter 07

The tools

Desktop apps, engines, servers and web interfaces each do a different job, and the right one depends on your hardware and how many people will use it.

Engine, app and interface

Engine
Does the calculation. llama.cpp, MLX, vLLM and SGLang are engines. Most have no window of their own: you start them from the command line and other programs talk to them.
Desktop app
Bundles an engine with a model downloader and a chat window. Ollama, LM Studio and Jan are desktop apps.
Web interface
A chat page that connects to an engine over the network. Open WebUI is a widely used example. It adds user accounts, chat history and document upload, and does not run models itself.

Most of these tools offer an OpenAI-compatible API, which accepts the same requests as OpenAI's online service. Programs written for that service can use your local model once you change the address they send requests to.

Why so many apps use llama.cpp

llama.cpp is an open-source engine that runs on almost any hardware: NVIDIA, AMD, Intel and Apple graphics, or a plain processor. Jan, KoboldCpp, llamafile and the llama.cpp team's own desktop app run it directly. LM Studio uses llama.cpp and can also use Apple's MLX on a Mac. Ollama started on llama.cpp and now runs many models on its own engine, built on ggml, the library at the core of llama.cpp. New model types therefore often work in llama.cpp first and reach the apps a little later.

Which engine for which job

One person, any hardware
llama.cpp or an app built on it. It runs on Windows, macOS and Linux, with or without a graphics card, and can split a model between graphics memory and system RAM.
Many users, large graphics cards
vLLM or SGLang on Linux servers. They serve many conversations at once efficiently, but expect the whole model to fit in graphics memory and reserve most of that memory when they start.
Apple silicon Macs
MLX, directly or through LM Studio or Ollama. It is often faster than llama.cpp on the same Mac.
Laptops with an NPU
An NPU is a chip built for AI tasks. Lemonade uses the NPU in AMD Ryzen AI laptops and OpenVINO the one in Intel Core Ultra laptops. Both need specially prepared models.

Chapter 08

Model files

The same model is published in several formats and sizes, and the file name tells you which one you are looking at.

Common formats

GGUF
One file that holds the weights, usually quantised, together with the settings needed to run them. Used by llama.cpp and the apps built on it. The usual choice for laptops, desktops and Macs.
Safetensors
The format labs use for their original releases, usually at 16-bit and split into several files. Used by vLLM, SGLang and Hugging Face's own libraries. Unlike older .bin and .pt files, a safetensors file cannot run hidden code when it is loaded.
MLX
Weights converted for Apple's MLX engine, often at 4-bit or 8-bit. Many are published by the mlx-community organisation on Hugging Face.
AWQ and GPTQ
Two ways of storing a model at 4-bit for graphics-card servers running vLLM, SGLang and similar engines.
FP8, MXFP4 and NVFP4
Compact 8-bit and 4-bit number formats that newer NVIDIA graphics cards can calculate with directly. Many labs now publish official files in these formats.
EXL3
The format of the ExLlamaV3 engine for NVIDIA graphics cards. It keeps good quality at low bit counts.

What Q4_K_M means

Q4 means about 4 bits per weight. K stands for the “K-quant” method, which stores weights in small groups that each have their own scale. M stands for medium: some of the most sensitive parts of the model are kept at 6-bit. The S (small) variant keeps nearly everything at 4-bit. On average a Q4_K_M file uses about 4.9 bits per weight, and it is the usual default for llama.cpp and the apps built on it.

Where to download

Almost all open models are published on Hugging Face (huggingface.co), a website that hosts model files.

Official repositories sit under the lab's own organisation name. The lab publishes the original weights there, usually as safetensors.

Community uploads convert official weights into GGUF and other formats. Widely used uploaders include unsloth, bartowski, ggml-org (the llama.cpp team) and lmstudio-community. Their files contain the same model in another format. When a lab publishes its own GGUF files, those are the safest choice.

Spotting a fine-tune

A fine-tune is a model someone trained further on their own data. Its Hugging Face page lists the original under “base model”. Names that add words such as uncensored, abliterated or merge, or a person's or company's name in front of the lab's model name, usually mark community variants. They can be useful, but the original lab has not tested them, and they may behave differently.

Checking a download

  • Check that the organisation name matches the lab exactly. Copies with similar names exist.
  • Prefer GGUF and safetensors. Older .bin, .pt and .pkl files can contain code that runs when the file is loaded.
  • Read the licence file in the repository before using the model at work (chapter 12).
  • Look at the upload date and the number of downloads. A new upload with few downloads deserves more caution.
Chapter 09

Images, video and speech

Picture, video and voice models keep no conversation memory; picture size, clip length and the number of steps set how much memory and time they need.

Most image and video models are diffusion models. They start from random noise and remove a little of it in each of many steps until a picture appears, guided by your text. There is no conversation, so context length and conversation memory do not apply. Three things set the cost instead: the picture size, the number of frames for video, and the number of steps.

Making a picture takes far more calculation than writing a paragraph, so calculating power matters more here than memory speed. Graphics cards have a large lead over processors, and usually over Macs as well.

Why video is the hardest

A five-second clip at 16 frames per second has 80 frames. The model works on all of them together so that motion stays consistent, comparing every part of every frame with every other part. Memory and time therefore grow faster than the clip length: a clip twice as long takes more than twice the time.

What typically fits where

The main tools

ComfyUI is where most new image and video models appear first. Diffusers is the Python library behind many tools, and stable-diffusion.cpp is an image engine built on the same library as llama.cpp. For speech, whisper.cpp and faster-whisper turn audio into text, while Piper and Kokoro read text aloud.

Chapter 10

From one person to a team

A shared service adds user logins, a web interface, document search and someone who keeps it running.

On your own computer, one app does everything. A service for a team or a company splits the work into parts, so that each part can be secured, scaled and replaced on its own. The diagram shows the usual set-up.

Sizing the hardware

The number that matters is how many people wait for an answer at the same moment. It is far lower than the number of staff, because people read, think and type between questions. Each of those conversations needs its own conversation memory, and all of them share the machine's speed.

Running it safely

Keep data inside
Run the service in your own network or in a cloud account your company controls. Switch off optional online features and usage statistics in each tool. Decide whether chat history is stored, and for how long.
Never expose an engine to the internet
Engines such as Ollama, llama.cpp and vLLM listen on a network port. Ollama's API has no login at all, and the others offer only simple keys. Let only the gateway reach them, and put the gateway behind HTTPS and your company login.
Log with care
Record who used which model and how much, so you can plan capacity and investigate misuse. Logging the full text of prompts creates a store of sensitive data; decide on purpose whether to do it, who may read it and when it is deleted.
Plan updates
Engines and models are updated often, with fixes and speed gains. Try a new version on a test machine first and keep the previous version ready to switch back.
Back up what you cannot download again
Model files can be downloaded again. Settings, user accounts, chat history and the document index cannot. Back them up and test a restore.

When a paid API still makes sense

A mixed set-up often works well. Everyday and sensitive work runs locally, while tasks that need the strongest models, or rare peaks in demand, go to a paid online service through the same gateway. Write down which data may leave the company, and enforce that rule in the gateway where you can.

Chapter 11

What it costs

You can pay per token, rent a graphics card by the hour or buy your own hardware, and the amount of steady use decides which costs least.

There are four common ways to use an open model, and each is paid for differently. This chapter explains how they are priced, so that the figures on the Costs page make sense.

Online services charge per token

Online AI services measure use in tokens, the pieces of words described in chapter 4. A token is about three quarters of an English word, so 1,000 tokens are roughly 750 words. Most other languages need more tokens for the same text.

Prices are quoted per million tokens, because a single token costs only a tiny fraction of a cent. Most price lists show two prices. Input tokens are everything sent to the model: your question, any documents, the instructions the app adds and, in a chat, the conversation so far. Output tokens are the text the model writes back. Output usually costs several times as much as input, because the model writes one token at a time but reads the input in large batches.

In a chat, the app sends the whole conversation again with every new message, so the input grows with each turn. Many providers charge less for cached input: text that repeats the beginning of a recent request, such as a long set of instructions or the earlier part of a chat. The size of the discount, and how long the text stays cached, differ between providers.

Thinking models (chapter 4) write out their reasoning before the answer. Providers bill these tokens as output, even when the app hides them, so a thinking model can cost much more for an answer of the same length.

One summary, worked out

Summarising a 10-page report sends about 6,500 input tokens and returns a one-page summary of about 650 output tokens. At example prices of €0.50 per million input tokens and €2 per million output tokens:

6,500 × €0.50 ÷ 1,000,000 + 650 × €2 ÷ 1,000,000 ≈ €0.0046, about half a euro cent. A thousand such summaries cost about €4.55.

Other things that change the bill

Some providers charge less for requests that may wait several hours, which suits large jobs such as processing an archive. Some charge a higher rate when a prompt is very long. Models for pictures, speech and video are usually priced per picture, per minute of audio or per second of video instead of per token. Price lists for businesses usually show prices before VAT.

Four ways to pay

The Costs page compares four ways of using a model. They differ in how you pay, who handles your data and how much of the work is yours.

Pay per token

A hosted API for an open model

A provider runs an open model on its servers, and your chat app or program sends requests to it over the internet. You pay for the tokens you use and nothing in a month you use none, and there is no hardware to look after. The provider processes your prompts and documents, so its terms, and the country where it runs the model, decide what you may send. Because the model is open, you can later move to another provider or to your own hardware and keep the same model.

Left to you: picking a provider whose terms suit your data, and the app or program that sends the requests.

Pay per hour

Renting a GPU

A cloud provider rents you a machine with one or more graphics cards. You install an engine and the model yourself, as on your own computer, and pay for every hour the machine is switched on, whether it is busy or idle. You decide which model and version run, and the machine works only for you, although it stands in the provider's data centre under the provider's terms. On-demand machines can be started and stopped at any time. Reserved machines are booked for months or years at a lower hourly price.

Left to you: setting up, securing and updating the software, and switching the machine off when nobody needs it.

Pay once

Buying hardware

You pay for the machine once, then for electricity and upkeep. Everything runs on hardware you control, at home, in the office or in your own server room, which gives you the most say over your data and over when anything changes. The machine costs the same whether it is busy or idle, so its cost per token falls the more it is used.

Left to you: all of it, from installation and security to repairs, backups and replacement.

Pay per seat or per token

Paid closed assistants

A closed model is one whose weights are not published, so you can use it only through the vendor's own service. You pay either a fixed monthly fee per person, called a seat, for a ready-made chat app, or per token through the vendor's API. On hard tasks the leading closed models usually do better than models that fit on ordinary hardware. The vendor sets the prices and the terms for your data, and decides when models change or are retired. The Costs page shows these services for reference only, because they run different models from the open one you are pricing.

Left to you: checking the vendor's terms and data settings, for example whether your chats may be used to train its models.

What owning hardware costs

The price of the machine is only part of what it costs. Everything it costs over its working life, added together, is called the total cost of ownership.

The purchase, spread over years
To compare a purchase with a monthly bill, divide the price by the number of months you expect to use the machine. This is called amortisation. A machine bought for €3,000 and used for three years costs about €83 a month, however much or little it is used.
A computer for the cards
Graphics cards are sold on their own. They need a host computer with a power supply, cooling, a processor, system memory and storage. For one or two gaming cards that is an ordinary desktop PC. For four or eight server cards it is a special server that adds a large share of the price. The Costs page adds the host computer when it prices bare cards.
Electricity
A graphics card at full load draws a few hundred watts, and a server with eight cards several kilowatts, plus the cooling to carry the heat away. An idle machine still draws some power: the Costs page assumes about 15% of its full draw.
Staff time
Someone has to install, update, secure and repair the system. On a personal computer that is your own time. For a company service it is part of someone's job and can cost more than the electricity. On the Costs page you can add these hours under “Change assumptions”.
Spares and replacement
Hardware fails and ages. A service that people depend on needs a spare machine, a repair contract or a fallback such as a hosted API. After a few years, newer hardware does the same work with less electricity, and the old machine is worth little.
Prices that move
Prices for graphics cards and memory change quickly, and in 2026 they have been unusually unstable, with AI data centres buying a large share of the supply. Check prices on the day you decide, and treat every price in this guide as an example.
Used cards
Second-hand graphics cards cost less and can be a sensible way to start. They usually come with little or no warranty, may have run at full load for years, and older models lack features that newer engines use, such as the compact FP8 format (chapter 8).

Utilisation decides the cost per token

Utilisation is the share of time the hardware is actually working. A machine costs much the same each month whether it answers ten questions or ten thousand, so its cost per token depends mainly on how busy it is. For example, a machine that costs €100 a month in total and produces 100 million tokens costs €1 per million tokens. If it produces 10 million, each million costs €10.

A hosted API charges the same price per token at any volume, because the provider keeps its machines busy with many customers' requests. Buying therefore costs least when use is high and steady. A team's use is rarely steady: most requests arrive in working hours, and the machine must be large enough for the busiest hour, so it stands idle at night and at weekends.

Working out the electricity

Multiply the power in watts by the hours the machine runs and divide by 1,000 to get kilowatt-hours (kWh). Then multiply by your price per kWh. Example: a PC that draws 400 watts for 8 hours on 22 working days uses 400 × 8 × 22 ÷ 1,000 ≈ 70 kWh a month. At an example price of €0.25 per kWh that is about €18 a month. Household and business prices differ, and the Costs page lets you choose a region.

When buying costs less than paying per token

Break-even is the point at which two options have cost the same in total. Before it, the option that was cheaper to start is ahead; after it, the option with the lower monthly cost is. The chart shows when a machine you buy reaches that point against a hosted API, for the amount of use you set.

Which option suits whom

Just me

If you use AI a few times a day, a hosted API or a chat subscription costs little, and a new machine bought only for this rarely saves money. Running a model on a computer you already own adds little more than electricity and keeps your data with you, so it is worth trying if a model that fits is good enough for your tasks. People who buy hardware for personal use usually do it for privacy, to work offline or to learn.

A small team

At low or uncertain volume, paying per token is cheaper and leaves nothing to maintain. A shared machine pays off when the team uses it heavily every working day. It is also the usual choice, at any volume, when client data may not leave the office. Renting a GPU suits a trial: run the model you would buy hardware for, measure the real use for a few weeks, then decide.

A company

Steady, high volume across many people can keep servers busy enough to pay off, and owning them gives full control over data and versions. Spiky or short work, such as processing an archive once or a project lasting a few months, suits rented GPUs or a hosted API, because you pay only while the work runs. Many companies combine the two: their own servers for everyday and sensitive work, and a hosted service for peaks (chapter 10).

For a company, data protection and the place where the model runs often matter more than price: which data may go to which provider, in which country and under which contract. Some hosted providers run open models in the EU, and the Costs page names one when its price list has it. Check these questions with your company's own legal and compliance people; this guide cannot answer them for you.

Chapter 12

Licences in plain words

Every downloadable model comes with a licence; most allow commercial use, and some add conditions for large companies or hosted services.

Open weights and open source

Most models in this guide are open-weight: you may download and run the trained weights. That does not include the training data or the code used for training. A few projects publish all of it, for example Olmo from Ai2 and Apertus from the Swiss AI Initiative, both in the model list. The Open Source Initiative published a definition of open-source AI in 2024 that asks for the weights, the code and detailed information about the training data.

Licence types you will meet

Permissive
Apache-2.0 and MIT allow use, changes and commercial use by companies of any size. You keep the licence text and copyright notices.
Custom, with conditions
Commercial use is allowed within limits: a revenue level above which you need a paid licence, a separate agreement for companies that sell access to the model as an online service, or a duty to show the model's name in your product.
Non-commercial
Research and personal use only. The popular XTTS-v2 voice model is an example.
Gated
On Hugging Face, a gated model asks you to sign in and accept its terms before downloading, and some wait for approval. Apertus 1.5 is gated this way.

This is a simplified summary and does not replace legal advice. Licences change between versions, so read the licence file in the model's repository and ask your legal team before your business depends on a model. The programs you use have licences too; the tool list in chapter 7 notes them.

Chapter 13

Glossary

Every term used in this guide, explained in one or two sentences.

Active parameters

In a mixture-of-experts model, the parameters actually used for each token. They set the speed, while the total sets the memory needed.

Amortisation

Spreading the price of a purchase over the months or years it is used, so that it can be compared with a monthly bill. For hardware, accountants call this depreciation.

API

An agreed way for one program to send requests to another. Engines offer an API so that chat apps and your own programs can use the model.

AWQ and GPTQ

Two methods for storing a model at 4-bit, used on graphics-card servers with engines such as vLLM and SGLang.

Bandwidth

How many gigabytes per second a memory can deliver. It sets the upper limit for how fast a model writes.

Base model

A model straight after its main training, before it was taught to follow instructions. For chat you want the instruction-tuned version, often marked “it” or “Instruct”.

Batching

Working on several users' requests in the same step. The weights are read once for all of them, so the machine's total output grows.

BF16 and FP16

16-bit number formats. Most models are trained and first published in BF16, which takes 2 bytes per parameter.

Break-even

The point at which two options have cost the same in total. After it, the option with the lower monthly cost is ahead.

Cached input

Input that repeats the beginning of a recent request, such as a long instruction or the earlier part of a chat. Many providers charge less for it.

Closed model

A model whose weights are not published. You can use it only through the vendor's own app or API.

Concurrent users

People waiting for an answer at the same moment. It is much lower than the total number of users, and it decides how much hardware a shared service needs.

Context

All the text a model can see at once: instructions, conversation, documents and its own answer. It is measured in tokens.

CPU

The computer's main processor. It can run models from system RAM, but more slowly than a graphics card.

CUDA, ROCm, Metal and Vulkan

Software layers that let programs calculate on graphics cards: CUDA for NVIDIA, ROCm for AMD, Metal for Apple, and Vulkan for cards from most makers.

Dense model

A model that uses all of its parameters for every token.

Diffusion model

A model that makes pictures or video by removing noise step by step, guided by a text description.

Embedding

A list of numbers that represents the meaning of a piece of text. Texts with similar meaning get similar numbers, which makes search by meaning possible.

Engine

The program that loads a model and calculates its output, for example llama.cpp, MLX or vLLM. Also called an inference engine or runtime.

Fine-tune

A model trained further on extra examples to change its style or teach it a field. Fine-tunes by third parties are not tested by the original lab.

FP8, MXFP4 and NVFP4

Compact number formats at 8 and 4 bits that newer graphics cards can calculate with directly. Many models are now released in them.

Gated repository

A model page on Hugging Face where you must sign in and accept the terms before downloading.

Gateway

A single entry point in front of the model servers. It handles logins, limits, logging and routing to the right model.

GGUF

A single-file model format used by llama.cpp and the apps built on it. It holds the weights, usually quantised, and the settings needed to run them.

GPU

Graphics processing unit, the chip on a graphics card. It does many calculations in parallel and has fast memory of its own, which suits AI models.

Hosted API

A service that runs a model on the provider's servers and answers requests sent over the internet. You pay per token.

Hugging Face

The website where most open models are published and downloaded.

Inference

Running a trained model to get an output. Training builds the model; inference uses it.

Input and output tokens

Input tokens are the text sent to the model, including documents and the conversation so far. Output tokens are the text it writes. Output usually costs several times as much per token.

Interface

The part you work with: a chat window, a web page or your own program.

KV cache

The engine's store of intermediate results for every token in the context, called conversation memory in this guide. It grows with the context length and with the number of users.

LoRA

A low-cost way to fine-tune a model: a small add-on is trained while the original weights stay unchanged.

Mixture of experts (MoE)

A model design in which each token uses only a few of many expert blocks. It needs memory for all of them but writes about as fast as a smaller model.

MLX

Apple's framework for machine learning on Apple silicon Macs, also used to run language models.

Model as a service

Selling access to a model over the internet, for example as a paid API. Some licences require a separate agreement for this.

NPU

A chip built for AI calculations, found in many recent laptops. It uses little power but needs specially prepared models.

Offloading

Keeping part of a model in system RAM when it does not fit in graphics memory. It works, but more slowly.

On-demand and reserved

Two ways to rent graphics cards. On-demand machines are paid by the hour and can be stopped at any time. Reserved machines are booked for months or years at a lower hourly price.

Open weights

A model whose trained weights you may download and run. The training data and training code may not be included.

OpenAI-compatible API

An API that accepts the same requests as OpenAI's online service, so programs written for that service work with a local engine once you change the address.

Parameter

One of the numbers a model learned during training, also called a weight. Model sizes are counted in billions of parameters, written as B.

Precision

How many bits each parameter is stored with. Higher precision is more exact and takes more memory.

Price per million tokens

The usual unit for API prices, often given separately for input and output tokens. A million tokens are about 750,000 English words.

Prompt

The text you send to the model, including instructions and any documents.

Prompt processing

The engine reading the whole prompt before it starts writing. It is limited by calculating power, and a graphics card does it much faster than a processor.

Q4_K_M

A common GGUF quantisation level: about 4.9 bits per weight, with some sensitive parts kept at 6-bit.

QAT

Quantisation-aware training: training a model so that it expects to be stored at low precision. Its 4-bit version loses less quality.

Quantisation

Storing a model's weights with fewer bits to make the file smaller, at a small cost in quality.

RAG

Retrieval-augmented generation: searching your own documents for passages that match a question and adding them to the prompt, so that the model answers from them.

Reranker

A small model that sorts search results by how well they answer the question. It improves document search.

Safetensors

A file format for model weights that cannot run hidden code when loaded. Labs use it for their original releases.

Seat

A paid place for one person in a subscription, usually billed every month.

Steps

In image and video models, the number of rounds of noise removal. More steps take longer.

System RAM

The computer's main memory. It is larger and cheaper than graphics memory, and several times slower.

Tensor parallel

Splitting each layer of a model across several graphics cards so that they work on every token together. Server engines use it to run models larger than one card and to run them faster.

Thinking model

A model that writes out its reasoning before its answer. It does better on hard tasks and takes longer to start answering.

Token

A piece of text that the model reads or writes: a word, part of a word or a punctuation mark. 100 English tokens are about 75 words. Online services count and charge use in tokens.

Tokens per second

How fast a model writes. About 6 is enough to read along; 15 or more feels quick.

Total cost of ownership

Everything a machine costs over its working life: the purchase, the host computer, electricity, staff time, repairs and replacement.

Unified memory

One memory pool shared by the processor and the graphics part, as in Apple silicon Macs and AMD Ryzen AI Max machines.

Utilisation

The share of time hardware is actually busy. Hardware costs the same when idle, so higher utilisation means a lower cost per token.

Vector store

A database that stores embeddings and finds the ones closest to a question.

VRAM

The memory on a graphics card. It is fast but limited in size.

Weights

Another word for parameters: the learned numbers in a model file.

No term matches. Try a shorter word.
